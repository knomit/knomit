# Spike 2 report: knomit's event streams over Wails Streams (no listener)

Branch `spike/wails-asset-transport` (continues spike 1, Wails v3.0.0-beta.28). Evidence logs: `.claude/plans/2026-10-12-spike-wails-streams-run-streams.log` (page driving the Streams wire directly) and `...-run-ui-streams.log` (real UI). Head SHA: see the end.

## 1. Wails Streams API at beta.28 (module cache `github.com/wailsapp/wails/v3@v3.0.0-beta.28`)
- Go: `pkg/application/stream.go`. `app.HandleStream(name string, h func(*StreamConn))` (L719); names are EXACT, no wildcard, no path, query or headers (L728 map lookup). `StreamConn` has `Name()`, `Context()` (cancelled when the connection closes, L208), `Send/TrySend/SendJSON`, `Receive/ReceiveJSON`, `Close()`, `Window()`. "A connection's lifetime is its handler goroutine's lifetime" (L26-29): returning from the handler closes the stream. Send blocks on a full per-window queue (8 MiB / 256 frames, L66-85).
- JS: `internal/runtime/desktop/@wailsio/runtime/src/stream.ts`. `Stream(name)` returns synchronously a WebSocket-shaped `WailsSocket` (readyState CONNECTING, `onopen/onmessage/onclose/onerror`, `send`, `close`), frames are binary (`binaryType` defaults `arraybuffer`). Client close sends a close notice and the Go `Context()` is cancelled.
- It is exported from the ES module the framework serves at `/wails/runtime.js` (`bundledassets/runtime.js` exports `Stream`, `JSONStream`, `WailsSocket`), so the page does `await import('/wails/runtime.js')`: no `@wailsio/runtime` dependency in `web/` (same trade `web/src/externalLinks.ts` already makes).
- Because the name carries nothing, the adapter opens ONE stream name `knomit-sse` and sends the API path as the first frame (`{path}` JSON); the Go handler `ReceiveJSON`s it, validates `/api/v1/` and no `..`, and subscribes. This is also the natural place a per-window authority check would go (`c.Window()`).

## 2. Why Streams work with the buffered Windows writer (beta.28 source)
The Windows response writer buffers every response until the handler returns (`internal/assetserver/webview/responsewriter_windows.go` L33-110). Streams never ask it to stream. They are a request/response protocol:
- Go->JS is one parked GET (`serveStreamPoll`, `stream_transport.go` L190-240). It blocks in `awaitFrames` (`stream_session.go` L229-269) until at least one frame exists, then drains a batch (cap `streamMaxResponseBytes` = 1 MiB, `stream.go` L81-87, whose comment says outright that it exists because the Windows writer accumulates the whole body), writes it with a Content-Length, and RETURNS. Returning is exactly what makes the Windows writer deliver. If nothing arrives in `streamHoldTimeout` (20 s) it returns 204. A newer poll supersedes an old one.
- The JS client immediately issues the next poll (`stream.ts` L814-850, "no polling interval ... the server holds the request until a frame exists, so delivery latency is already ~0"), so the round trip is the batching window.
- JS->Go is a normal POST (`stream.ts` L683-780).
So on Windows each batch of events costs one completed HTTP response; per-event latency is one poll round trip (low milliseconds on loopback-free in-process IPC), not zero-copy streaming, and bursts are batched. No listener, nothing bound.
Cancellation on page close is the explicit close frame plus the session TTL (`streamSessionTTL` 60 s; `streamHoldTimeout` comment says a poll of a navigated-away page can linger up to 20 s "until cancellation is plumbed through"); for window close, `dropWindow`.
**Windows test to run later:** `KNOMIT_SPIKE_PROXY=1 KNOMIT_SPIKE_STREAMS=1 KNOMIT_SPIKE_PAGE=streams` (the same `spike_streams.html`): expect `open`, per-event arrival in order with per-event latency of ~one poll round trip (record numbers), `close()` followed by the upstream pipe count dropping within 2 s, resume after `/spike/drop`, a 1 MiB+ burst (logs backlog) splitting into `more` polls without loss, and the real UI with `KNOMIT_SPIKE_PROBE=1`. Also check a 3-minute idle (204 every 20 s) keeps the stream alive.

## 3. Implementation (spike, behind `KNOMIT_SPIKE_PROXY=1` + `KNOMIT_SPIKE_STREAMS=1`)
- `web/src/eventStream.ts`: `EventSourceLike`, `openEventStream(url)` (default `new EventSource(url)`; desktop `WailsEventSource` when `window.__KNOMIT_EVENT_TRANSPORT__ === 'wails-stream'`), frames `{t:'open'|'error'|'event', event, data, id}` mapped to open/error/named/message events with `lastEventId`; the six call sites now call it (`api.ts` x4, `App.tsx`, `logStore.ts`); `/config.js` gets the flag from `tools/desktop/spike_streams.go`.
- `tools/desktop/spike_streams.go`: per page stream, `auth.DialLocal` + `GET <path>` with `Accept: text/event-stream` (and `Last-Event-ID` when it has one), a full SSE parser (event/data multi-line/id/retry/comments), reconnect with backoff (500 ms doubling to 5 s, `retry:` honoured) resuming with the last id, upstream closed through the request context when the page closes or the connection ends. One non-pooled upstream connection per page stream so connections are countable. Spike proxy also strips `x-wails-window-*`.

## 4. macOS measurements (darwin arm64, WKWebView, scratch home, port 19394; the user's 19278 untouched)
Page = `spike_streams.html` using the real Wails `Stream` and the adapter's exact wire.
- **a. repo-events latency:** upstream event read -> frame sent -> page onmessage: 0-1 ms (index event 59.712 -> page 59.712; second 59.715 -> 59.715; `ready` 59.285 -> 59.285). Create -> first `index` event at the page 27 ms. Exactly one upstream subscription per open page stream: stats `{open:1}` after opening A, 4 after opening A + logs + branch (+1 idle proxy conn counted in the total).
- **b. close:** page `close()` -> upstream socket closed in under 1 ms (close() at 01.404, upstream conn closed 01.404, same millisecond) and handler `ctxErr=context canceled`; both the logs and branch streams, and A. Well inside 2 s. The Go side learns of the close through `StreamConn.Context()`.
- **c. resume:** closing the upstream from the desktop side while A was open: error frame to the page in 3 ms, reconnect after the 500 ms backoff, `open` + `ready` at the page at +553 ms; a repo created afterwards produced `index` events at the page (27 ms later): continuity after resume. **Server and Last-Event-ID today:** the server emits no `id:` fields and does not read `Last-Event-ID` (grep of `internal/web`); the adapter forwards the header when it has an id, so it is ready, but resume is satisfied only by the server's design: every connect sends `ready` and the UI refetches (fact 8e878292). No duplicates seen; events published while the stream was down would be lost, exactly as with a native EventSource reconnect today.
- **d. logs and branch streams:** logs: 28-line backlog + `ready` delivered in one burst in ~3 ms (30 frames), live lines per event after; branch stream `/repos/{repo}/branches/main/events` delivered its `status` event (frame in 1 ms). Both through the same handler.
- **e. real UI with the flag:** boots through the proxy and flag; opens exactly one `repo-events` stream and, with a repo selected, exactly one branch-events stream (the others open on their pages); no reconnect loop. After a forced upstream drop the resumed `ready` reached the page and the UI re-read `GET /api/v1/repos` and `/repos/railtest/origin` 103 ms later (the designed recovery path). **Not obtained:** a DOM read of the rail showing the new repo. The probe's page script was suspended by WebKit within about 3 s (no display in this session; same limit as spike 1), and the first-run UI sits on the wizard. So "rail updates" rests on the refetch evidence above, not on a seen rail.

## 5. Honest cost
- Lines added: web TS 213 (`eventStream.ts`) + 95 test = 308; call-site edits +25/-7 in `api.ts`, `App.tsx`, `logStore.ts`; Go 258 (`spike_streams.go`) + proxy/app glue ~20; test page 53. A production version drops the probe/log/test-page code and the `httptest` recorder; estimate roughly 150 Go + 215 TS + tests.
- NOT emulated: automatic reconnect by the page (the desktop reconnects, the page sees `error` with `readyState` CONNECTING then `open`; there is no page-side retry if the Wails stream itself ends, which gives CLOSED); `withCredentials`; `MessageEvent` fields other than `type`, `data`, `lastEventId` (no `origin`, `source`); `retry:` is honoured on the Go side only; per-frame size limit (`streamMaxFrameBytes`, ErrStreamTooLarge) and the 256-stream/page cap; `Last-Event-ID` resume depends on server support that does not exist. A stream that the server answers with non-200 is closed by the desktop (4xx) rather than surfacing the HTTP status.
- Unchanged: `streamOutage.ts` (it only needs `readyState` + error/open events, which the adapter provides, including `EventSource.CLOSED` = 2) and the vitest double / `test-setup.ts` (the default path still constructs the global `EventSource`, i.e. the double). `npx tsc -b` clean; `npx vitest run` 139 files, 1964 tests passed (Node v26.10.0); eslint clean on `eventStream.ts` and its test (the repo already has ~99 unrelated lint errors).
- Architectural costs: the page now depends on the Wails runtime module being importable at `/wails/runtime.js` (loaded lazily on first stream); every SSE path is reachable by any window via the stream name (use `c.Window()` to authorize, not done); fact ddceb81b recorded the maintainer's rule that logs stream "on the same API mount, not Wails IPC" and "the wails:// scheme handler cannot carry a WebSocket upgrade": this spike revisits it deliberately, Streams are not a WebSocket upgrade but the mount constraint is no longer literally true.
- The six non-stream calls remain on the asset handler (spike 1 proxy), which is fine on every platform.

## 6. Recommendation
Streams on every platform for the six SSE streams, plus the spike-1 asset-handler `/api` proxy (with the ContentLength=-1 fix and `x-wails-*` stripping) for request/response calls: that gives a single transport with no listener, no token and no per-platform split, and it is the only design verified by source to work with the Windows writer. macOS is proven end to end (sub-millisecond forwarding, immediate close, reconnect + `ready` refetch). The remaining risk is Windows behaviour in practice (poll round-trip latency, 20 s 204 cycle, burst batching), which the named Windows test settles; if it disappoints, the fallback is the loopback proxy on Windows only. Do not choose "asset-handler SSE on macOS/Linux + Streams on Windows": that keeps two paths for no gain, since Streams already work on macOS.
