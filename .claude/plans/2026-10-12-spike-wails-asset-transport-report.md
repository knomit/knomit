## 2. Source read at v3.0.0-beta.28 (module cache, `github.com/wailsapp/wails/v3@v3.0.0-beta.28`)
**Windows still buffers. The loopback-proxy premise (a) holds at beta.28.**
- `internal/assetserver/webview/responsewriter_windows.go` L33-48: the writer "deliberately does not implement http.Flusher"; "Write accumulates into an in-memory buffer that is only handed to WebView2 in Finish ... a streaming response cannot work on Windows today, independently of anything WebView2 does." L51 `rw.body.Write(buf)`; L67-110 `Finish` calls `resp.PutByteContent(rw.body.Bytes())` once. So `ReverseProxy FlushInterval: -1` flushes into a bytes.Buffer; an SSE stream delivers nothing until the handler returns (never, for SSE).
- macOS: `responsewriter_darwin.go` L96-122: each Write calls `URLSchemeTaskDidReceiveData` straight away, `Flush()` is a declared no-op because nothing is buffered. Linux (`responsewriter_linux.go` L55-72): Write goes into a pipe WebKit reads; `Flush()` no-op. Both stream.
- Sniffer (`assetserver/content_type_sniffer.go` L39-83) holds the first 512 bytes only when the handler sets no Content-Type; SSE sets one, so it passes through. `requestContextResponseWriter` (`assetserver_webview.go` L15-47) forwards Flush.
- **Cancellation changed (premise (b) is out of date at beta.28).** `assetserver_webview.go` L118 `ctx, cancel := webview.RequestContext(r)` and L168 `http.NewRequestWithContext(ctx, ...)`: the handler's r.Context() is the request lifetime context. It is cancelled by: macOS, `application_darwin.go` L446-449 `cancelURLRequest` -> `webview.CancelRequest` (`request_finalizer.go` L88-106, ctx wired at L47-75); Linux, `request_lifetime_linux.go` (cancel on WebKit abort); Windows, a CDP-based tracker (`pkg/application/request_cancellation_windows.go`, `webview_window_windows.go` L2438-2439 `tracker.Wrap`). Writes after cancel are discarded (`assetserver_webview.go` L20-31).
- Request dispatch: one goroutine per request (`assetserver_webview.go` L56-69, `dispatchWorkers` must stay 0), so long-lived streams do not starve the pool.
- Release notes beta.4..28 (GitHub releases, grepped for stream/SSE/cancel/assetserver/flush/abort): beta.9 "Cancel macOS and iOS asset request contexts when WebKit aborts the matching custom-scheme task (#5963)"; beta.20 "Cancel aborted Windows asset requests, including worker requests, while preserving keepalive handlers across navigation (#5963, #5969)"; beta.23 "Cancel aborted custom-scheme requests on Linux (#6126)"; beta.6 "Asset server preserves content-type sniffer errors and unwritten prefixes during flushing (#5931)"; beta.8 "Streams" (below). **No release note says the Windows writer streams.**
- Beta.8 added `app.HandleStream(name, handler)` / JS `Stream(name)`: Go->JS is "one held poll per window over the asset server", JS->Go a POST. That is a long-poll, which works on a buffering writer because each poll response ends. It is a possible Windows-only SSE substitute but needs a `web/` transport change (EventSource replacement) and is not a drop-in for `EventSource('/api/v1/repo-events')`. Not tested.

## 4. Spike handler (commit 2)
`tools/desktop/spike_proxy.go` (+ `spike_test.html`, 6 lines in `app.go`), enabled only by `KNOMIT_SPIKE_PROXY=1`. Requests under `/api/` go through `httputil.ReverseProxy{FlushInterval: -1}` whose Transport dials `auth.DialLocal(cfg socket)` with `DisableCompression`. The desktop still boots its own server; `config.js`/`/boot/status` now report the page origin (`wails://localhost`) as `__KNOMIT_API_BASE__`, so the UI calls are same-origin. Instrumentation: per-write timestamp in the handler, an open-upstream-connection counter, and `/spike/log` for page-side timestamps. `KNOMIT_SPIKE_PAGE=1` loads a test page that runs the measurements inside the real WKWebView.

**Two real findings from building it:**
1. **ReverseProxy silently drops POST bodies on this path.** Wails sets `req.ContentLength` only from a `Content-Length` header (`assetserver_webview.go` L196-200), which a WKWebView custom-scheme POST does not carry, so `ContentLength == 0` with a non-empty `Body`; `ReverseProxy` nils the body when `ContentLength == 0`. First symptom: every `POST /api/v1/repos` answered 400 "the request body is empty". Fix used: `if r.ContentLength == 0 && r.Body != http.NoBody { r.ContentLength = -1 }` before proxying. Any real implementation needs it (and a test with a body-carrying POST).
2. Wails injects `x-wails-window-id` / `x-wails-window-name` into asset requests (see recalled fact 33d2c8f8); the spike forwards them upstream untouched. A real proxy should strip them, like `Origin`.

- **b. ## 6. Windows verdict and the test a Windows run must do
**From source: the asset handler cannot carry SSE or any streaming response on Windows at beta.28.** Writes buffer until the handler returns (`responsewriter_windows.go` L33-51, L67-110) and there is no Flusher by design; only cancellation of aborted requests was added (beta.20). Unary `/api/*` calls (JSON, the 250 KB GET) would work. Because the UI uses SSE for `repo-events`, logs tail and session events, the handler-only transport is not acceptable on Windows.

Windows test to run (same a-d as macOS, scratch home, `KNOMIT_SPIKE_PROXY=1`, `KNOMIT_SPIKE_PAGE=1`, port not 19278; named pipe path is dialed by `auth.DialLocal`, which verifies the pipe owner):
- a. SSE: expect `A es.open` but **no `A event#` lines until the stream ends** (events appear in handler log but not the page); also check `ResponseController.Flush` returns `ErrNotSupported` in the handler. If events do arrive one by one, beta.28 source is wrong and the verdict changes.
- b. Cancel: `es.close()` / `abort()`, then `/spike/stats` open count within 2 s (the CDP tracker should cancel; verify it does for fetch-streams as well as EventSource).
- c. Large GET: SHA-256 equal to a direct pipe call (WebView2 `PutByteContent` of the whole buffer).
- d. Logs tail: expect nothing until close.
- Also: POST with body through the proxy (the ContentLength finding) and `304` handling (`responsewriter_windows.go` L83-88 rewrites 304 to 500).

## 7. Recommendation
Keep the design's loopback proxy (option b) as the transport on **Windows** (required), and on macOS/Linux it is now a free choice rather than a forced one: on macOS the handler-proxy streams per event, cancels in milliseconds, and is byte-exact, and needs no listener/token. But a per-platform split is the cd92bf55 failure shape (two transports kept in step), and the shared origin means every window including Settings reaches `/api`. If the user wants one transport everywhere, the loopback proxy with token is the only one that is verified-correct on Windows by source. If they accept two, the asset handler on macOS/Linux plus loopback on Windows is viable, but Linux was NOT run here (source says it streams and cancels). Either way upgrade to beta.28 independent of this decision: it built with no code change and gives request cancellation on all platforms. Fix to carry into any proxy: the ContentLength=-1 workaround and stripping `x-wails-*` headers.
